// 01 — MISSION BRIEF

PROJECT OVERVIEW

The goal was to build and deploy a web application using cloud infrastructure that is repeatable, automated and easier to maintain than a manually configured environment.

COMPUTE

ECS FARGATE

Runs the containerised application without requiring me to manage the underlying EC2 servers.

INFRASTRUCTURE

TERRAFORM

Provisions AWS resources as code using a modular structure with reusable infrastructure components.

DELIVERY

CI/CD PIPELINE

Uses GitHub Actions to automate the application image build, publishing and deployment workflow.

// 02 — SYSTEM ARCHITECTURE

HOW IT CONNECTS

A request travels from the browser through DNS and the load balancer before reaching a healthy application task.

01

USER

Browser sends an HTTPS request.

↓
02

ROUTE 53 + ACM

DNS directs the domain to the load balancer. ACM supplies its TLS certificate.

↓
03

APPLICATION LOAD BALANCER

Accepts HTTPS traffic and forwards requests to the target group over HTTP on port 3000.

↓
04

ECS FARGATE

Runs two desired application tasks in separate public subnets across two Availability Zones.

↓
05

NODE.JS APPLICATION

Serves the portfolio page and responds to health checks at /health.

Supporting services: Amazon ECR stores the Docker image, CloudWatch collects container logs, and security groups control network access.

// 03 — INFRASTRUCTURE AS CODE

BUILT WITH TERRAFORM

Instead of creating each resource manually in the AWS console, I organised the infrastructure into modules. This separates responsibilities and makes the configuration easier to understand and maintain.

01

VPC MODULE

Creates the network, two public subnets, internet gateway and routing configuration.

02

ALB MODULE

Configures the load balancer, listeners, target group and network access rules.

03

ECS MODULE

Defines the ECS cluster, Fargate task definition, service, desired task count and logging.

04

ECR + IAM MODULES

Creates the image repository and the permissions required for ECS task execution.

05

DNS + CERTIFICATE

Uses Route 53 for DNS and ACM for certificate validation and HTTPS on the load balancer.

// 04 — CONTINUOUS DELIVERY

FROM COMMIT TO CLOUD

GitHub Actions automates the release workflow so that application changes can be built and deployed consistently.

01

GIT PUSH

Code changes are pushed to GitHub.

02

BUILD IMAGE

Docker builds the application container image.

03

PUSH TO ECR

The image is published to Amazon ECR using a commit-based image tag.

04

DEPLOY

The deployment workflow updates the ECS service to use the intended image version.

WHY USE OIDC?

GitHub Actions uses OpenID Connect (OIDC) to obtain temporary AWS credentials through an IAM role, avoiding the need to store long-lived AWS access keys as GitHub secrets.

// 05 — SECURITY & RELIABILITY

BUILT WITH CONTROL

NETWORK SECURITY

SECURITY GROUPS

The load balancer accepts web traffic. ECS tasks accept application traffic on port 3000 only from the load balancer's security group.

ENCRYPTION

HTTPS + TLS

HTTP traffic on port 80 redirects to HTTPS on port 443, where the load balancer uses its ACM certificate.

OBSERVABILITY

CLOUDWATCH

Container logs are sent to CloudWatch Logs to help investigate application behaviour and errors.

HEALTH MONITORING

HEALTH CHECKS

The load balancer checks /health and uses the response to determine whether a task can receive traffic.

CONTAINERS

DOCKER

Packages the Node.js application and its runtime into an image that can run consistently across environments.

AVAILABILITY

MULTIPLE TASKS

A desired count of two tasks allows the service to run multiple application instances. Actual availability depends on task health and placement.
